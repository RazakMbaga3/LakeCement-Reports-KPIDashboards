# Deploying to DigitalOcean — guide for the Odoo/hosting team

This is the reference doc for whoever is standing up and maintaining the
production server — currently the Odoo team (India), GitHub `teckzilla007`.
It replaces `RUNBOOK.md` / `GO_LIVE_CHECKLIST.md` for hosting purposes: those
two describe an earlier on-prem Windows-server plan (`node-windows`,
PowerShell `Restart-Service`) that was superseded once the Managing
Director moved production hosting to the cloud under the Odoo team's
ownership (`TECHNICAL_SPEC.md` §10). Everything here targets a Linux
droplet instead.

## 0. How you get the code 

You already have GitHub access — use it. The repo owner (`RazakMbaga3`)
adds `teckzilla007` as a collaborator on:

```
https://github.com/RazakMbaga3/LakeCement-Reports-KPIDashboards
```

On the droplet, `git clone` it once, then every future update is `git
pull` (or, once CI/CD is wired up per §3, nothing at all — it happens
automatically). This is strictly better than a source-code zip: no
re-transferring files by hand, full history if something needs to be
diffed or rolled back, and one source of truth instead of two copies
drifting apart.

You do **not** need push access — read access is enough to clone and pull.

## 1. Architecture in one paragraph

Static HTML/JS/CSS frontend (repo root — `login.html`, `dashboard.html`,
`sales.html`, etc.) served by Nginx → `/api/*` reverse-proxied to a
Node/Express backend (`backend/server.js`, port 5000, process-managed by
**pm2**) → PostgreSQL. All KPI math runs server-side
(`backend/services/formulaEngine.js` + `forms/formula-registry.js`);
browsers queue writes offline and sync automatically. The backend runs its
own scheduled jobs in-process via `node-cron` — morning digest (06:00),
watchdog alerts (every 15 min), nightly `pg_dump` backup (02:30) — no
external cron needed.

## 2. First-time droplet setup

### 2.1 Create the droplet

- Ubuntu 22.04 LTS (or newer LTS), 1–2 GB RAM is plenty for this app alone
  (size up if Postgres or Odoo shares the box).
- Enable the DigitalOcean firewall: allow **22** (SSH), **80**, **443**
  only. Everything else (Postgres 5432, app port 5000) stays internal —
  never expose those publicly.

### 2.2 System packages

```bash
sudo apt update && sudo apt upgrade -y

# Node 22 LTS (NodeSource — installs system-wide to /usr/bin, so it's on
# PATH for non-interactive SSH sessions too, which matters for §3's CI/CD)
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs nginx git

# pm2 — process manager, replaces the Windows-only node-windows service
sudo npm install -g pm2

# Only if Postgres runs on this same droplet (see 2.4 for the alternative)
sudo apt install -y postgresql postgresql-contrib

# HTTPS certificates
sudo apt install -y certbot python3-certbot-nginx
```

### 2.3 Deploy user + SSH keys

Don't run the app as root. Create a dedicated user:

```bash
sudo adduser --disabled-password --gecos "" deploy
sudo usermod -aG sudo deploy   # only if this user also administers the box
```

Two **separate** SSH keypairs get used here — keep them distinct, they do
different jobs:

| Key | Connects | Lives where |
|---|---|---|
| **Deploy key** | GitHub repo → droplet (`git pull`) | Private half stays on the droplet only |
| **CI key** | GitHub Actions → droplet (SSH login to run the deploy script) | Private half stored as a GitHub Actions secret |

**Deploy key** (as the `deploy` user, on the droplet):
```bash
ssh-keygen -t ed25519 -C "lake-cement-deploy" -f ~/.ssh/deploy_key -N ""
cat ~/.ssh/deploy_key.pub
```
Give that **public** key to `RazakMbaga3`, who adds it under the repo's
**Settings → Deploy keys → Add deploy key** (read-only — do *not* check
"Allow write access"). Then, still as `deploy`:
```bash
mkdir -p ~/.ssh
cat >> ~/.ssh/config <<'EOF'
Host github.com
  IdentityFile ~/.ssh/deploy_key
EOF
```

**CI key** — generated by whoever sets up the GitHub Actions workflow
(§3), *not* on the droplet. Its **public** half gets appended to the
droplet's `~/.ssh/authorized_keys` for the `deploy` user; its private half
becomes the `DO_SSH_KEY` GitHub secret.

### 2.4 Database — pick one

**Option A — Postgres on the same droplet** (simplest, matches the
original RUNBOOK design):
```bash
sudo -u postgres psql -c "CREATE USER lcl_admin WITH PASSWORD '<strong password>';"
sudo -u postgres psql -c "CREATE DATABASE lcl_mis OWNER lcl_admin;"
sudo -u postgres psql -c "ALTER USER lcl_admin CREATEDB;"  # needed for restore drills
```
`.env`: `DB_HOST=localhost`, `DB_PORT=5432`, `DB_SSL` left unset/false.

**Option B — DigitalOcean Managed Database** (DO handles backups,
failover, patching for a monthly fee):
Create the cluster + a `lcl_mis` database in the DO control panel, then
in `.env`: `DB_HOST=<cluster-host>`, `DB_PORT=25060` (or whatever DO
gives you), `DB_USER`/`DB_PASSWORD` from the cluster credentials, and
**`DB_SSL=true`** — the app's connection pool
(`backend/db/index.js`) already supports this, it's just off by default.
If you go this route, skip the local `pg_dump` backup cron in §4 — DO's
managed backups replace it (still worth confirming retention meets your
needs).

Pick whichever matches what you're already running for Odoo's own
database — no strong preference from the app side.

### 2.5 Clone, configure, initialize

```bash
sudo mkdir -p /var/www/lake-cement-dashboard
sudo chown deploy:deploy /var/www/lake-cement-dashboard
cd /var/www/lake-cement-dashboard
git clone git@github.com:RazakMbaga3/LakeCement-Reports-KPIDashboards.git .

cd backend
cp .env.example .env
```

Edit `.env` (see full field list/comments in `backend/.env.example`).
The ones that must change from the template:
- `DB_*` — from §2.4
- `JWT_SECRET` — generate a real one:
  `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`
- `ALLOWED_ORIGIN` — the real public URL, e.g. `https://mis.lakecement.co.tz`
  (never leave this as `*` in production)
- `TRUST_PROXY=1` — required, since Nginx sits in front
- `BACKUP_DIR` — see §4
- SMTP + `DIGEST_TO` / `ALERT_TO` if email alerts are wanted

Then:
```bash
npm ci --omit=dev
node db/init.js        # or: psql -f db/schema.sql, then npm run migrate
npm run migrate
npm run seed            # creates default users — everyone must change
                         # their password on first login (must_change_password)
npm test                 # lint + smoke — must be green before going further
```

### 2.6 Run it with pm2

Use `deploy/ecosystem.config.js` (already in the repo):
```bash
cd /var/www/lake-cement-dashboard
pm2 start deploy/ecosystem.config.js
pm2 save
pm2 startup   # prints a sudo command — run exactly what it prints, once,
              # so the app survives a reboot
```

Sanity check: `curl http://127.0.0.1:5000/api/health` → `"status":"ok"`.

### 2.7 Nginx + HTTPS

```bash
sudo cp deploy/nginx.digitalocean.conf /etc/nginx/sites-available/lake-cement
sudo ln -s /etc/nginx/sites-available/lake-cement /etc/nginx/sites-enabled/
sudo nano /etc/nginx/sites-available/lake-cement   # set the real server_name
sudo nginx -t && sudo systemctl reload nginx

# HTTPS (only once a domain name points at this droplet's IP — certbot
# can't issue a cert for a bare IP address)
sudo certbot --nginx -d mis.lakecement.co.tz
```

### 2.8 Verify before calling it done

- [ ] Open the site in a browser, log in.
- [ ] `curl https://<domain>/api/health` → `"status":"ok"`.
- [ ] **Reboot the droplet** and confirm the site + `/api/health` come back
      with no manual step (`pm2 startup` + Nginx's own systemd unit should
      handle this).
- [ ] `pm2 logs lake-cement-mis` shows no repeated errors.

## 3. Ongoing updates — automatic deploy on push

This repo ships `.github/workflows/deploy.yml`. Once the two secrets
below are set, **every push to `main` automatically deploys** — no one
needs to SSH in manually for routine updates.

### What happens on each push

1. Developer pushes to `main` on GitHub.
2. GitHub Actions runs `.github/workflows/deploy.yml`.
3. It SSHes into the droplet (using the **CI key** from §2.3) and runs
   `deploy/deploy.sh`, which:
   - `git fetch` + `git reset --hard origin/main` (via the **deploy key**
     from §2.3 — the droplet never needs a person's GitHub credentials)
   - `npm ci --omit=dev` (only reinstalls if `package.json` changed)
   - `npm run migrate` (applies any new `db/migrations/*.sql`)
   - `pm2 reload ecosystem.config.js` — reload, not restart, so pm2 starts
     the new process before killing the old one (near-zero downtime)

`.env` is never touched by this — it's gitignored and stays local to the
droplet, so secrets never pass through GitHub Actions or git history.

### One-time setup (whoever administers the droplet + repo secrets)

In the GitHub repo, **Settings → Secrets and variables → Actions**, add:

| Secret | Value |
|---|---|
| `DO_HOST` | the droplet's IP or domain |
| `DO_USER` | `deploy` |
| `DO_SSH_KEY` | the **private** half of the CI key from §2.3 |
| `DO_PORT` | only if SSH doesn't run on 22 |

That's it — the workflow is already written and will start firing on the
next push to `main`.

### Rollback

Automatic deploy means a bad push goes live immediately — there's no
manual gate. To roll back:
```bash
git revert <bad-commit>   # or: git reset --hard <last-good-commit> --
git push                  # triggers a fresh auto-deploy of the good state
```
Or, directly on the droplet as `deploy`, for something urgent:
```bash
cd /var/www/lake-cement-dashboard
git reset --hard <last-good-commit>
cd backend && npm ci --omit=dev && npm run migrate
pm2 reload ecosystem.config.js
```

If you'd rather have a human gate every deploy instead (review the diff,
then deploy on purpose), change the workflow trigger from `push` to
`workflow_dispatch` in `.github/workflows/deploy.yml` — same script,
just fired by clicking "Run workflow" on GitHub instead of on every push.

## 4. Backups

Same mechanism as the original RUNBOOK, just Linux paths. Only relevant
if you picked Option A (self-hosted Postgres) in §2.4 — DO Managed
Database backups replace this for Option B.

- Set `BACKUP_DIR` in `.env` to somewhere **other than the app/DB disk** —
  a mounted volume or a second disk. A backup on the same disk as the
  database isn't a backup.
- `pg_dump` needs to be on `PATH` (it is, after `apt install postgresql`)
  — leave `PG_BIN` empty.
- Nightly dump runs automatically via `BACKUP_CRON` (default 02:30, set
  in `.env`) — no OS-level cron needed, it's in-process.
- `npm run restore:drill` — run monthly; restores the newest dump into a
  scratch database, verifies it, drops it. Never touches the live DB.

## 5. Reaching Odoo from the cloud

`ODOO_URL` / `ODOO_DISPATCH_URL` in `.env` currently point at
plant-internal addresses (see `TECHNICAL_SPEC.md` §12, item 8). Since the
same team now hosts both this app and Odoo, the simplest fix is putting
the droplet on the same private network / VPC as Odoo (or a VPN/tunnel
between them) rather than exposing Odoo's API publicly. Whoever sets up
the droplet should confirm which of those is in place before wiring up
`ODOO_SYNC_CRON` — until then, leave it `off` and the app runs fine
without the Odoo pulls (they're additive, not required for core
functionality).
